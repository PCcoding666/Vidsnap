# VidSnap Slim 产品边界

Last reviewed: 2026-06-10

本文档用于定期清理 VidSnap Slim 的产品边界。它不是愿景文档，而是当前版本的执行约束：AI、工程实现、验收和排期都应以这里的边界为准。

## 一句话定义

VidSnap Slim 是一个面向本地视频文件的轻量视频理解工具：用户上传本地视频，系统完成转录、总结、历史记录和基于视频文本上下文的问答。

## Slim Core 可执行定义

“当前 Slim 只做本地视频上传、转录、总结、历史和基于文本上下文的问答”不是一句功能描述，而是一条产品契约。它定义的是一条确定的数据流：用户把一个本地视频交给系统，系统把视频中的语音内容转成结构化文本，再把文本转成摘要、历史资产和可追问上下文。

### 1. 本地视频上传

本地视频上传的定义：

- 用户从自己的设备选择一个视频文件，并通过前端上传到后端。
- 系统只接受明确支持的视频文件格式。
- 系统不主动从外部 URL、视频平台、云盘或直播流抓取内容。
- 上传成功只代表文件已进入处理链路，不代表转录、总结或问答已经完成。

数据边界：

- 输入：`File` 对象或 multipart/form-data 中的 `video_file`。
- 输出：后端临时文件路径、基础视频 metadata、后续处理需要的 `video_id`。
- 中间态：上传中、已接收、格式拒绝、处理失败。

异常闭环：

- 未选择文件时，前端不应提交。
- 空文件名或缺失文件时，后端返回 400。
- 格式不支持时，后端返回 400，并列出可上传格式。
- 上传后的临时文件必须在成功或失败后尝试清理。

完成标准：

- 用户能从 UI 上传一个支持格式的视频。
- API 能通过 `/api/v1/video/process` 接收该文件。
- 不支持格式不会进入后续 AI 处理链路。
- 上传失败不会留下用户无法理解的空白状态。

### 2. 转录

转录的定义：

- 系统从视频中提取或使用音频内容。
- 系统调用语音识别服务，把语音转成文本段落。
- 转录结果是 Slim 后续总结和问答的主要事实来源。

数据边界：

- 输入：视频文件或分离后的音频文件。
- 输出：转录全文、转录段落、时间戳、语言、置信度。
- 中间态：音频抽取中、识别中、识别成功、识别失败。

异常闭环：

- 视频无音轨时，应返回明确的无可转录内容或降级信息。
- 语音服务不可用时，应返回可读错误，不应伪造转录。
- 转录为空时，后续总结和问答不得假装已有视频内容。

完成标准：

- 有清晰音频的视频能生成非空文本。
- 转录段落可以被保存、展示和作为问答上下文使用。
- 转录失败时，前端能显示失败原因或可恢复路径。

### 3. 总结

总结的定义：

- 系统基于转录文本生成视频内容摘要。
- 总结只对已获得的文本负责，不对画面中但未进入文本上下文的信息负责。
- 总结的价值是帮助用户快速判断视频主题、关键内容和是否值得继续追问。

数据边界：

- 输入：转录文本、转录段落、基础视频 metadata。
- 输出：摘要文本，可选的 brief、standard、detailed 三种粒度。
- 中间态：等待转录、生成中、生成成功、生成失败。

异常闭环：

- 没有转录时，不应生成看似确定的视频总结。
- LLM 服务不可用时，应保留已完成的转录结果。
- 总结失败不能抹掉已经成功的上传和转录状态。

完成标准：

- LLM 可用且转录非空时，系统能生成可阅读摘要。
- 摘要能在前端展示并复制。
- 摘要内容不能声称分析了当前 Slim 不支持的视觉细节。

### 4. 历史

历史的定义：

- 历史是用户已经提交过的视频处理记录。
- 历史用于让用户回到过去的视频结果，而不是做跨视频知识库。
- Slim 阶段的历史服务于连续使用体验，不等于团队资产管理或长期归档系统。

数据边界：

- 输入：登录用户身份、分页或数量限制。
- 输出：视频 ID、标题、时长、创建时间、处理状态、详情入口。
- 中间态：无历史、加载中、加载失败、未登录。

异常闭环：

- 匿名用户请求历史时，应返回空列表和登录提示。
- 登录用户只能读取自己的视频。
- 数据库不可用时，应明确提示服务不可用或加载失败。

完成标准：

- 登录用户能看到最近处理过的视频。
- 用户点击已完成视频后，能加载总结和转录详情。
- 用户不能通过 video_id 越权访问其他用户的视频详情。

### 5. 基于文本上下文的问答

文本问答的定义：

- 问答只基于当前视频的转录文本、摘要和 metadata。
- 系统可以引用相关时间片段，但不承诺画面级视觉理解。
- 问答的目标是降低用户查找视频内容的成本，而不是替代通用聊天机器人。

数据边界：

- 输入：`video_id`、`session_id`、用户问题、当前视频转录上下文。
- 输出：回答文本、可选时间片段引用、会话状态。
- 中间态：会话初始化中、可提问、回答生成中、上下文缺失、回答失败。

异常闭环：

- 未完成处理的视频不应进入可问答状态。
- 缺少转录上下文时，应返回明确错误。
- 模型回答不得编造视频未提供的信息。
- 关键帧参数存在时，也不能把 Slim 定义扩大成视觉问答能力。

完成标准：

- 视频处理完成后可以创建聊天会话。
- 用户提问时，系统能基于当前视频文本回答。
- 回答可以关联到转录时间片段。
- 上下文不足时，系统明确说明无法回答。

### 6. 这条产品契约不包含什么

这条定义明确排除：

- 从 URL 下载视频。
- 理解画面里但没有出现在转录中的信息。
- 对视频做剪辑、字幕烧录或二次创作。
- 批量处理和跨视频检索。
- 团队协作、分享、评论、审批。
- 企业级长期存档和合规审计。

### 7. 为什么只做这些

Slim 的商业和产品判断是：先把“一个本地视频变成文本资产”这条主路径做稳定。用户愿意继续使用 VidSnap 的最小理由，不是平台支持多少入口，而是一次上传后能可靠得到可读总结、可查转录和可追问答案。

因此，任何新功能如果不能提升这条路径的成功率、质量、速度、成本效率或复用价值，都不应进入 Slim Core。

## 当前北极星

让用户用最少操作，把一个本地视频转成可阅读、可搜索、可追问的知识文本。

当前优先级：

1. 上传成功率和处理稳定性。
2. 转录与总结的可用质量。
3. 历史记录和问答上下文的连续性。
4. 成本可控，避免不必要的多模态和存储开销。

不以“功能看起来完整”为目标。Slim 阶段优先交付一条可靠路径，而不是扩展所有视频平台、所有媒体形态、所有协作场景。

## 当前产品内边界

### 输入

只支持本地视频文件上传。

允许格式：

- MP4
- MOV
- MKV
- AVI
- WEBM
- M4V

当前不支持 URL 输入、YouTube 下载、直播流、批量上传、文件夹导入、云盘导入。

### 核心处理链路

当前主链路：

1. 前端选择本地视频文件。
2. 后端接收上传并写入临时目录。
3. 后端抽取或处理音频。
4. Paraformer-v2 完成语音转录。
5. LLM 基于转录文本生成总结。
6. 可选写入 Supabase，用于用户历史记录、转录段落、总结和处理状态。
7. 前端展示总结、转录、历史记录，并创建视频问答会话。

这条链路必须保持确定性：每次任务都应有明确的 `video_id`、处理状态、错误信息、临时文件清理路径和可解释的返回结构。

### 输出

当前必须输出：

- 视频处理状态。
- `video_id`。
- 转录文本或转录段落。
- 文本总结。
- 基础 metadata。

登录用户在 Supabase 可用时，还应支持：

- 最近视频历史。
- 视频详情读取。
- 配额检查和使用量递增。

### 问答

当前问答以视频文本上下文为主。

允许能力：

- 基于转录内容回答问题。
- 返回相关时间片段。
- 保持单个视频会话上下文。

边界限制：

- 不承诺视觉级别的精确理解。
- 不承诺跨视频全局知识库检索。
- 不承诺长期聊天记忆。
- 不把示例聊天、静态推荐问题或 UI 占位文案视为已完成的 AI 能力。

## 当前产品外边界

以下能力在 Slim 阶段默认不做，除非先更新本文档：

- YouTube URL 下载与解析。
- 多平台视频导入。
- 关键帧驱动的多模态分析。
- 视觉定位、画面 OCR、动作识别、人物识别。
- 实时 WebSocket 进度推送的产品承诺。
- 多用户协作、团队空间、共享链接。
- 视频剪辑、字幕烧录、导出视频。
- 复杂订阅计费闭环。
- 企业级权限、审计、合规报表。
- 移动端原生 App。

历史文档中出现过的“云原生多模态视频分析平台”“YouTube 输入”“关键帧场景检测”等描述，当前只能视为历史方向或保留接口，不代表 Slim 当前边界。

## 技术边界

### 后端

当前后端边界：

- FastAPI 提供上传、处理、历史、详情、聊天相关接口。
- 视频文件先进入本地临时目录。
- 转录依赖阿里云 DashScope/Paraformer-v2。
- 总结依赖 LLM 服务可用性。
- Supabase 是用户、历史、转录和总结的持久化层。
- OSS 上传是可选能力，不应成为本地处理主链路的唯一成功条件。

必须闭环的异常路径：

- 未上传文件。
- 不支持格式。
- 认证失败但允许匿名处理的路径。
- 登录用户配额耗尽。
- Supabase 不可用。
- LLM 不可用。
- 转录失败。
- 临时文件清理失败。

### 前端

当前前端边界：

- 主界面是上传、处理状态、总结、转录、历史和右侧问答。
- 上传入口只接受本地视频。
- 历史记录依赖登录态和后端数据。
- 关键帧 UI 可以保留兼容入口，但不得暗示 Slim 已完成视觉分析能力。

前端不应新增会让用户误以为已支持的入口，例如 URL 输入框、YouTube 图标、批量上传按钮、视觉识别标签。

## 性能与成本硬约束

Slim 阶段不追求毫秒级实时响应，追求长任务可完成、失败可解释、成本不失控。

最低约束：

- 上传接口必须流式分块写入，避免一次性读入完整文件。
- 单次处理失败必须返回可读错误，不允许静默卡死。
- 临时文件在处理完成或失败后应尝试清理。
- LLM 总结不可阻塞基础转录 metadata 的生成逻辑。
- 关键帧提取默认不应带来额外视觉分析成本。

暂不承诺：

- 大文件并发处理能力。
- 弱网断点续传。
- 后台任务队列级别的可靠重试。
- 跨实例任务恢复。
- 明确 SLA。

当要进入下一阶段，必须先定义：

- 单文件最大体积。
- 单视频最大时长。
- 最大并发任务数。
- 平均处理耗时目标。
- 单视频可接受成本上限。
- 失败重试策略。

## 验收标准

一个 Slim 版本功能只有同时满足以下标准，才算完成。

### 上传与处理

- 支持格式内的视频可以提交到 `/api/v1/video/process`。
- 不支持格式返回 400，并给出明确格式提示。
- 处理成功返回 `status=success` 和 `video_id`。
- 处理失败返回可读错误，不吞异常。
- 临时文件在成功或失败后均有清理逻辑。

### 转录与总结

- 有音频的视频应产生非空转录，或明确返回转录失败原因。
- LLM 可用时应产生总结。
- LLM 不可用时，系统应保留转录/metadata 的可用路径，而不是把整个产品体验定义为失败。

### 历史与详情

- 匿名用户请求历史时返回空列表和登录提示。
- 登录用户可以看到自己的最近视频。
- 登录用户不能访问其他用户的视频详情。
- Supabase 不可用时返回明确服务不可用或降级信息。

### 问答

- 完成处理的视频可以启动聊天会话。
- 问答请求必须绑定 `session_id` 和 `video_id` 上下文。
- 回答应基于当前视频的转录或已保存 metadata。
- 如果上下文缺失，应返回明确错误，而不是编造视频内容。

### UI

- 上传入口只表达本地视频上传。
- 处理中、成功、失败三种状态可区分。
- 总结和转录可阅读、可复制。
- 历史为空、未登录、加载失败三种状态可区分。
- 不展示当前不可用能力作为主路径。

## 语义消融规则

为了避免用文学语言替代工程语言，需求描述中出现以下词时，必须补充可验证定义：

- “流畅”：说明具体等待状态、按钮禁用、进度反馈、错误恢复方式。
- “智能”：说明基于什么输入、输出什么结构、失败时怎么降级。
- “稳定”：说明覆盖哪些异常路径，如何复现。
- “快速”：说明目标耗时、文件大小、视频时长和网络条件。
- “准确”：说明评估样本、人工对照、错误容忍度。
- “支持”：说明入口、接口、数据模型、持久化和验收用例。
- “优化”：说明优化指标、当前基线和目标值。

任何无法转成验收标准的描述，不进入开发任务。

## 体验边界

Slim 的体验应该克制、明确、低认知负担。

应该做到：

- 用户第一眼知道只能上传本地视频。
- 处理期间知道系统正在工作。
- 失败时知道下一步该换文件、登录、重试还是检查配置。
- 结果页优先展示总结和转录，不用装饰性内容占据主空间。
- 问答入口只在有视频上下文后变成可用状态。

不应该做到：

- 用营销式文案掩盖产品能力不足。
- 用复杂动画拖慢处理型工具的操作路径。
- 把保留接口包装成已上线功能。
- 在 Slim 阶段引入过度订阅、排行榜、社交分享等偏离主链路的增长功能。

## 定期边界清理机制

建议每周或每个功能分支合并前做一次边界清理。

### 清理问题

1. 这个改动是否服务于“本地视频转成可阅读、可搜索、可追问的知识文本”？
2. 它是否新增了当前产品外边界中的能力？
3. 它是否让用户误以为某个未完成能力已经可用？
4. 它是否增加了处理成本、存储成本或外部 API 依赖？
5. 它是否有可复现的验收标准？
6. 它失败时是否有清晰的异常路径？
7. 它是否需要更新数据模型、配额模型或权限模型？

### 决策标签

每个新增需求必须归入一个标签：

- `Slim Core`: 当前必须做，直接强化主链路。
- `Slim Support`: 支撑主链路的可靠性、配置、日志、测试、部署。
- `Deferred`: 有价值，但不进入当前 Slim。
- `Out of Scope`: 与当前北极星无关，应删除或不做。
- `Evidence Needed`: 缺少用户、成本、技术可行性或验收证据。

### 更新规则

当以下任一情况发生时，必须更新本文档：

- 新增输入源。
- 新增 AI 能力类型。
- 新增持久化对象。
- 新增用户角色或权限。
- 新增付费/配额规则。
- 改变关键处理链路。
- 把历史保留接口重新变成产品承诺。
