# Task evaluation: harness + model vs native video models

This page defines how VidSnap measures its three business tasks, how it compares
"harness + model" with a model that reads the video natively, and how the report
turns the comparison into "optimise component X" or "swap model Y". It is the
method; it publishes no results.

The evaluation code lives in `src/vidsnap/eval/` and the CLI group `vidsnap eval`.
Eval sets live in `benchmarks/eval/`. Every evaluated run is an ordinary
RunBundle written by `HarnessKernel` with the v0.1.1 trace format
([trace-format.md](trace-format.md)); the evaluator reads those traces and never
keeps a second log. Results, rendered outputs, RunBundles, media and run indexes
stay outside the repository.

## Tasks

| Suite | Task | Output (one JSON object) |
|---|---|---|
| `t1` | Long video to an illustrated WeChat-style article | title, intro, 3-10 takeaways, sections with figures (timestamp + caption), summary |
| `t2a` | Explainer video: source video + topic to a storyboard (script, captions, visuals) rendered to timeline HTML | title, scenes (narration, captions, on-screen text, source timestamps) |
| `t2b` | Podcast / clip review for clips of at most 120 s | summary, claims with start/end seconds |
| `t3` | Teacher screen recording to wrong-question records, illustrated study notes and an HTML teaching video storyboard | `wrong_questions`, `notes`, `video` |

`t2a` and `t2b` are the two "scenario 2" candidates of the 2026-10-06 scenario
research: the explainer-video pipeline (topic, script, HTML, render) and the
podcast review pilot (summary plus claims on clips up to 120 s).

HTML for `t2a` and `t3` is rendered by a deterministic template
(`vidsnap.eval.render`) from the model's storyboard, following the timeline
convention of one scene list, one clock and one caption source from which the
script and SRT are generated. The model is graded on the storyboard; asking it to
hand-write the animation is a separate, later decision.

## Eval set format (`vidsnap.eval-suite/v1`)

One JSON file per task in `benchmarks/eval/suites/`. Each item:

| Field | Meaning |
|---|---|
| `item_id`, `status` | `ready` (source and references complete), `needs_reference` (source documented, reference outputs still to be written) or `placeholder` (a slot for the owner's video) |
| `source.kind` | `synthetic` (generated by `scripts/eval/make_synthetic_media.py`), `public` (documented URL and licence) or `owner` |
| `source.path` / `url` | Path relative to the media root, and where the file came from |
| `source.sha256`, `bytes`, `duration_seconds`, `licence`, `attribution`, `language`, `has_audio` | Identity and provenance; no media is committed |
| `source.generator` | For synthetic items, the storyboard spec the file is generated from |
| `source.clip` | Optional `[start, end]` window cut from the source before the run |
| `inputs` | The goal and, for `t2a`, the topic and audience |
| `reference.transcript` | Timed reference transcript; synthetic items derive it from their spec |
| `reference.key_points` | Facts a good output must contain, as keyword groups (all groups must match, any alternative per group), with modality (`speech`, `visual`, `both`) and an optional time window |
| `reference.key_moments` | Timestamps (with tolerance) a figure, scene or claim should point at |
| `reference.entities` | Exact strings (names, numbers, formulas) that must be spelled correctly |
| `reference.forbidden` | Statements that would be hallucinations for this video |
| `reference.questions` | `t3` only: the wrong questions, their answers (with `answer_option` for multiple choice, so `C` counts) and the mistake explained |

The media root defaults to `benchmarks/eval/media/` (git-ignored) and can be set
with `--media-root` or `VIDSNAP_EVAL_MEDIA_ROOT`. A source whose bytes do not match
the recorded SHA-256 is refused for `public` and `owner` items; synthetic files can
differ across machines (TTS and FFmpeg versions), so a mismatch is a warning and the
actual hash is recorded in the result.

`vidsnap eval validate <suite>` checks a suite and lists every placeholder and
missing reference.

## Systems

A system name is chosen from an allow-list; models, endpoints and prompts are
fixed per system and recorded in the run header.

| System | What runs |
|---|---|
| `harness+<model>` | `HarnessKernel` with `FixedPolicy`: probe, `transcribe_audio` (Qwen ASR), `sample_evidence` (`AdaptiveSampler`), one synthesis call to `<model>` with the transcript and frames, the task's verifier gates, at most one targeted repair round |
| `harness+<model>+oracle-asr` | Same, but ASR returns the reference transcript (ablation) |
| `harness+<model>+oracle-frames` | Same, but frame candidates are the reference key moments (ablation) |
| `harness+<model>+frame-labels` | Same, with a `[frame-id @ MM:SS]` text label before every image (candidate fix) |
| `native:<model>` | `HarnessKernel` with `NativePolicy`: probe, then one request that sends the whole video file (Base64 `video_url`) and the task prompt to a video-capable model with its own defaults; no ASR, sampling, verifier repair or retries |
| `harness+mock`, `native:mock` | Deterministic offline providers for tests and plumbing checks |

Allowed models: `qwen3.8-max` (harness default), `qwen3.8-flash`, `qwen3.8-omni-flash`
for `harness+`; `qwen3.8-omni-flash`, `qwen3.5-omni-plus`, `qwen3.8-max` for `native:`.
The harness and native systems receive the same task instructions and the same
output schema; only the input path differs.

Endpoints and keys (environment variables only, never files):

| Endpoint | Base URL | Key variables |
|---|---|---|
| `dashscope` (default) | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `VIDSNAP_DASHSCOPE_API_KEY`, then `DASHSCOPE_API_KEY` |
| `token-plan` | the harness default Token Plan endpoint | `VIDSNAP_QWEN_API_KEY`, then `QWEN_API_KEY` |

The Token Plan catalogue does not include `qwen3-asr-flash` or any Omni model
(`/models` listing and a `model_not_found` reply, 2026-10-10), so ASR and native
Omni systems always use `dashscope`. A `qwen3.8-omni-flash` or
`qwen3.5-omni-plus` request with the whole file as `data:;base64,` in a
`video_url` part, `stream=True`, `stream_options.include_usage` and
`modalities=["text"]` was accepted and answered on 2026-10-10; the model's
default (thinking on) was left unchanged.

Native input: a file whose Base64 form is under the documented 10 MB limit is sent
as-is; a larger file is re-encoded locally (lower resolution and bitrate, audio kept)
until it fits, and the trace records the original and sent sizes. A video that
cannot fit is refused with a `validation` failure; the DashScope temporary-upload
path used by `vidsnap.benchmark.url_probe` is the documented next step for long
videos.

## Running

```bash
vidsnap eval validate t1
vidsnap eval run --suite t1 --system harness+qwen3.8-max \
  --price-table prices.json --max-cost 5 --items t1-syn-01
vidsnap eval run --suite t1 --system native:qwen3.8-omni-flash \
  --price-table prices.json --max-cost 5 --items t1-syn-01
vidsnap eval report eval-out/*.json --human human.json -o report.md
vidsnap eval regrade eval-out/*.json   # after references change; no model calls
```

Live systems refuse to start without `--price-table` and `--max-cost`. The runner
stops before the next item once the measured cost reaches the cap; a run whose
cost cannot be measured stops the suite, because unknown is never zero.

Each item becomes one RunBundle under the runs root (indexed in `index.jsonl`
like any other run) plus rendered outputs (`article.md`, `notes.md`,
`wrong_questions.json`, `video.html`, `captions.srt`, extracted figure images)
under `--out`. One results file (`vidsnap.eval-result/v1`) per suite and system
holds, per item: run id, bundle path, terminal state, failure category, duration,
tokens, cost, the machine scores and the per-stage metrics.

## Machine metrics

All machine metrics are deterministic string and timestamp checks; no model judges
another model.

| Metric | Tasks | How |
|---|---|---|
| `success` | all | Output parsed into the task schema and the run ended `SUCCEEDED` or `PARTIAL` |
| `key_point_coverage` | all | Weighted share of reference key points whose keyword groups all match the output text (NFKC, case-folded, whitespace and punctuation removed) |
| `entity_recall` | all | Share of reference entities spelled exactly in the output |
| `hallucinations` | all | Number of forbidden statements matched |
| `moment_recall` | t1, t2a, t2b, t3 | Share of reference key moments with an output timestamp (figure, scene source, claim span, question frame) within tolerance |
| `timestamps_out_of_range` | all | Share of output timestamps outside `[0, duration]` |
| `structure` | all | Mean of the task's structure checks (t1: title, intro, 3-10 takeaways, at least 3 sections, at least 3 captioned figures, figures spread over half the timeline, mostly Chinese prose, summary length; t2a/t3 video: 3-15 scenes, scene length 6-40 s, captions at most 6 s and 40 characters, no overlap, SRT identical to captions; t3 questions: every field filled) |
| `question_recall`, `answer_accuracy`, `mistake_coverage`, `question_time_accuracy`, `question_precision` | t3 | Reference wrong questions matched by stem keywords; answer, mistake explanation and timestamp checked for each match; spurious questions lower precision |
| `html_valid`, `render_ok` | t2a, t3 | Rendered HTML parses; with `--render-check`, headless Chrome (all host names unresolvable) renders a non-blank frame |
| `latency_ms`, `tokens`, `cost`, upload bytes | all | From the RunBundle: run span duration, model-request usage and request bytes, ASR audio sent (Base64), price table |
| `failure_category` | all | `vidsnap.run-failure/v1` category from the trace |

## Human metrics

Machine metrics cannot judge prose quality, whether a figure is the right figure,
errors outside the reference key points, teaching correctness for a student, or
whether the owner would publish. Those come from people.

`vidsnap eval review build --a <results> --b <results> -o review.html` writes one
offline page: for each item it shows two outputs side by side as A and B in a seeded
random order, with the task's Chinese rubric (1-5 per dimension with anchors at 1,
3 and 5), a preference and an estimated editing time. The page saves scores to a
JSON file the reviewer downloads; the A/B key is written to a separate file and the
page never sees it. `vidsnap eval review import scores.json --key key.json -o
human.json` un-blinds the scores into `vidsnap.eval-human/v1`, which `vidsnap eval
report --human` aggregates. Publishing decisions and real editing minutes for a
real run go through `vidsnap runs review` as before.

## Component attribution

The harness is a pipeline: probe, ASR, frame sampling, synthesis, verifier and
repair. For every harness item the evaluator derives per-stage metrics from the
RunBundle (evidence files and events) and the reference:

| Stage | Metric | Needs |
|---|---|---|
| ASR | `asr_cer` (Chinese, characters) or `asr_wer` (English, words) of the transcript evidence against the reference transcript; `asr_timed` (whether the evidence has internal timestamps) | reference transcript |
| Sampling | `frame_moment_recall`: share of reference key moments with a sampled frame within tolerance; frame count and timeline spread | key moments |
| Synthesis | `evidence_key_point_coverage` (key points present in the evidence the model saw) vs `key_point_coverage` (present in the output) | key points |
| Verifier / repair | gate pass rates, repair rounds used, whether the repair round changed the score | trace |
| Time and cost | share of run time and cost per stage (probe, ASR call, sampling call, model request) | trace, price table |

Each missed key point is assigned to the first stage that lost it:

- `speech` key point not in the transcript evidence: `lost_at_asr`.
- `visual` key point with no sampled frame inside its window: `lost_at_sampling`.
- Present in the evidence (or a frame was sampled in its window) but not in the
  output: `lost_at_synthesis`.
- No reference transcript or window: `unattributed`.

Ablations confirm the attribution: `+oracle-asr` and `+oracle-frames` replace one
component with the reference, so the gain over the plain harness on the same
items bounds what improving that component can buy. Model swaps (`harness+<other
model>`) and native systems run on the same items answer "swap model Y".

The report states a conclusion only when the data supports it (at least 3 scored
items for the stage):

- Optimise ASR when at least 30% of misses are `lost_at_asr` and `+oracle-asr` gains
  at least 0.10 key-point coverage, or `asr_cer` exceeds 0.15.
- Optimise sampling when at least 30% of misses are `lost_at_sampling`, or
  `frame_moment_recall` is below 0.7 while `+oracle-frames` gains at least 0.10
  moment recall.
- Optimise synthesis (prompt or model) when at least 30% of misses are
  `lost_at_synthesis`; swap the model when another `harness+<model>` beats it by at
  least 0.10 on the primary metric at no more than 1.5 times the cost.
- Prefer native for a task when a native system beats the best harness system on
  the primary metric by at least 0.10 and on human preference.

Otherwise the report says the evidence is insufficient. These thresholds are
starting points, documented here so they can be changed in one reviewed place
(`vidsnap.eval.report`).

## Cost

Run cost comes from the trace: model-request tokens times the price table, plus
ASR seconds (the logged `transcribe_audio` windows) times the ASR price. A failed
ASR call is charged as an upper bound and flagged
(`speech_failed_charged_as_upper_bound`). Amounts are list-price equivalents;
free quotas, Token Plan quota and discounts are not visible to the evaluator.
Native Omni usage is split by modality when the provider reports it
(`prompt_tokens_details`), because some models price audio input differently.
The evaluator's price table is `vidsnap.eval-price-table/v1`: a `vidsnap.price-table/v1`
model table plus optional `audio_input_per_million_tokens` per model and
`speech_per_second` for ASR models. VidSnap ships no prices;
`benchmarks/eval/price-table.example.json` is an example with its source and date,
to be checked before use.

`vidsnap eval report --estimate` prints an estimated cost per task and system for
the ready items, from their durations and the stated assumptions (tokens per
second of video for native models, tokens per frame and per second of transcript
for the harness); it is an estimate, not a measurement.

## Limitations

- Synthetic videos (slides plus TTS narration) are clean; they measure the pipeline,
  not robustness to real recordings. The owner's videos are the real test.
- Keyword matching misses paraphrases that use none of the listed alternatives and
  can be satisfied by an output that mentions a keyword in the wrong sense; the
  human rubric covers both.
- Native systems see a re-encoded file when the original exceeds the Base64 limit;
  the trace records it and the report marks those items.
- `t2a` and `t3` HTML is template-rendered; model-written HTML is not graded.
